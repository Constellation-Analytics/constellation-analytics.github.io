Inventory Health Dashboard
— Retail Distribution

A Power BI dashboard built for a fictional mid-sized retail distributor to replace weekly manual Excel stock reports. Connects to a PostgreSQL data model to surface overstock, understock, and slow-moving SKU risk across 8 warehouses in near real-time.

Background

Meridian Distribution manages stock across eight warehouse locations for a network of independent grocery and homewares retailers. Their weekly stock health process involved a senior planner pulling data from their WMS into Excel, manually joining it to a supplier lead time spreadsheet, and producing a static summary table that was emailed to three separate teams by Thursday afternoon.

The process worked, in the way that slow, manual processes work: it produced output, but at significant cost. Any mid-week stock event — an unexpected delivery, a large customer order, a supplier delay — was invisible until the following week's report. By that point, the opportunity to act had usually passed.

The brief was to replace the weekly email report with a dashboard that refreshed daily, covered the same KPIs, and was accessible to all three teams without needing to wait for Thursday.

🎯

Problem: Weekly manual Excel stock reports created a 5-day blind spot for inventory events. Three teams needed the same data and were getting it at different times through an unreliable process.

Data Model

Before any dashboard work began, the data model needed to be correct. The WMS exported flat transaction files — one row per stock movement — which meant the analytical layer had to aggregate these into a usable stock position view. This was done in PostgreSQL using a set of SQL views that Power BI connects to directly.

Stock position view

The core view calculates current on-hand stock per SKU per warehouse by summing all receipts and subtracting all outbound movements since the last physical stocktake. A separate supplier lead time table joins on SKU to enable days-of-cover calculations.

SQL 
-- mart.v_stock_position: current on-hand by SKU and warehouse
CREATE OR REPLACE VIEW mart.v_stock_position AS
WITH movements AS (
    SELECT
        sku_code,
        warehouse_id,
        SUM(CASE WHEN movement_type = 'RECEIPT'   THEN qty ELSE 0 END) AS total_in,
        SUM(CASE WHEN movement_type = 'OUTBOUND'  THEN qty ELSE 0 END) AS total_out,
        MAX(movement_date)                                               AS last_movement
    FROM wms.stock_movements
    WHERE movement_date >= (SELECT stocktake_date FROM config.last_stocktake LIMIT 1)
    GROUP BY sku_code, warehouse_id
),
base AS (
    SELECT sku_code, warehouse_id, qty_on_hand AS stocktake_qty
    FROM wms.stocktake_positions
    WHERE stocktake_date = (SELECT stocktake_date FROM config.last_stocktake LIMIT 1)
)
SELECT
    b.sku_code,
    b.warehouse_id,
    b.stocktake_qty + COALESCE(m.total_in, 0) - COALESCE(m.total_out, 0) AS qty_on_hand,
    m.last_movement,
    s.supplier_lead_days
FROM base b
LEFT JOIN movements m USING (sku_code, warehouse_id)
LEFT JOIN ref.supplier_lead_times s USING (sku_code);

Inventory Risk Classification

The most important design decision in the project was how to classify SKUs by risk. The old Excel report used static thresholds — anything below 14 days of cover was flagged red. This produced too many false positives for fast-moving SKUs with short lead times, and missed genuine risk for slow-moving SKUs with 60-day supplier lead times.

The new approach calculates days of cover relative to supplier lead time. A SKU is at risk when days of cover drops below a multiple of its lead time, rather than a fixed absolute threshold.

ℹ️

Days of cover = quantity on hand divided by average daily sales velocity over the trailing 28 days. Risk threshold = 1.5x supplier lead time. This catches genuine stock risk without over-alerting on fast movers with reliable short-lead suppliers.

DAX classification measure

DAX 
Stock Risk Status =
VAR DaysOfCover =
    DIVIDE(
        SUM(StockPosition[qty_on_hand]),
        AVERAGEX(
            DATESINPERIOD('Calendar'[Date], TODAY(), -28, DAY),
            [Daily Units Sold]
        )
    )
VAR LeadDays = SELECTEDVALUE(StockPosition[supplier_lead_days], 30)
VAR RiskThreshold = LeadDays * 1.5

RETURN
    SWITCH(
        TRUE(),
        ISBLANK(DaysOfCover),        "No Velocity",
        DaysOfCover < LeadDays,      "Critical",
        DaysOfCover < RiskThreshold, "At Risk",
        DaysOfCover > LeadDays * 8,  "Overstock",
        "Healthy"
    )

The Dashboard

The finished dashboard has four pages. The executive summary is the default landing page for most users. Planners typically navigate directly to the SKU drill-down. The warehouse comparison page was added at the client's request after they saw the prototype.

SKU drill-down

A table of all SKUs with current stock position, days of cover, risk classification, and days since last movement. Conditional formatting colours the risk column. Clicking any SKU row cross-filters the trend chart on the right to show that SKU's stock level over the trailing 90 days.

Red shading on the trend chart marks any period where stock fell below the risk threshold — giving planners immediate visual context for how long a problem has been developing, not just whether one exists today.

Warehouse comparison

A small multiples layout showing the risk distribution for each of the eight warehouses side by side. This page was not in the original scope but was straightforward to add once the data model was in place.

Python Data Preparation

The WMS export files arrived as semicolon-delimited text with inconsistent encoding across warehouses. A short Python script standardises the encoding, validates the expected column structure, and loads the cleaned files to the PostgreSQL staging schema. GitHub Actions runs this script nightly before the Power BI dataset refresh.

Python 
import pandas as pd
import psycopg2
import os
from pathlib import Path

EXPECTED_COLS = {'sku_code', 'warehouse_id', 'movement_type', 'qty', 'movement_date'}

def load_wms_export(filepath: Path) -> pd.DataFrame:
    df = pd.read_csv(filepath, sep=';', encoding='latin-1')
    df.columns = df.columns.str.strip().str.lower()
    missing = EXPECTED_COLS - set(df.columns)
    if missing:
        raise ValueError(f"Missing columns in {filepath.name}: {missing}")
    df['movement_date'] = pd.to_datetime(df['movement_date'], dayfirst=True)
    df['qty'] = pd.to_numeric(df['qty'], errors='coerce')
    return df.dropna(subset=['sku_code', 'qty', 'movement_date'])

exports  = list(Path('data/wms_exports').glob('*.csv'))
combined = pd.concat([load_wms_export(f) for f in exports], ignore_index=True)

conn = psycopg2.connect(os.environ['NEON_CONNECTION_STRING'])
combined.to_sql('stock_movements', conn, schema='wms', if_exists='replace', index=False)
conn.close()

Reduction in false-positive risk flags vs. fixed threshold approach

The planning team identified two overstock situations in the first month that would have been missed under the old fixed-threshold approach. Both SKUs had days of cover well above 14 days, but relative to their supplier lead times they were significantly overstocked.

Reflections

The data model work took longer than expected because the WMS transaction history had gaps — periods where the stocktake table had no matching record, causing incorrect stock positions for some SKUs. Auditing the source data before designing the SQL views would have caught this earlier.

The lead-time-relative risk threshold was a significant improvement, but it introduced a new dependency: the supplier lead time reference table needs to be kept current. This was flagged to the client as an ongoing data maintenance requirement.

The natural next step would be a demand forecasting layer. The current dashboard shows where stock is relative to recent velocity, but it does not anticipate future demand shifts.
