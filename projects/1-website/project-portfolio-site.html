Building My Website
as a Non-Developer

How I designed and built this website from scratch using HTML and CSS, a short foundational course, and an iterative AI-assisted workflow (without any prior web development experience).

Why Build It At All

As a data analyst and analytics engineer, most of my work lives inside client environments. Dashboards that aren't mine to share, pipelines in I can't publish, and outputs that go into internal reporting systems. I wanted something I could point people to that showed actual work, in a form I had full ownership of.

The obvious option was a template site. Something like Wix or a pre-built portfolio template would have taken just a few hours to build. And that’s exactly what I did… and it cost me $300AUD per year… for a pretty average website. So this year I decided to change that.

Not only am I saving money, but I'm also gaining valuable skills. Building something from scratch, even imperfectly, is the best possible learning experience and tells a lot more about how you approach problems you don't already know how to solve.

I had no web development background going into this. My experience was SQL, Python, and Excel. Front end languages like HTML and CSS were things I had seen in passing but never written. The question was whether I could produce something that looked even remotely professional without spending months learning a new discipline.

Building the Foundation

The 4-hour HTML/CSS course

Before writing a single line of site code, I completed a short introductory HTML and CSS course — roughly four hours of structured content. The goal was not to become a web developer. It was to understand the vocabulary well enough to have a productive conversation with an AI assistant, and to be able to read and reason about the output it produced.

That distinction matters. There is a significant difference between using AI to write code you cannot evaluate, and using AI to write code you can read, question, and modify. The course gave me enough to do the latter. I came out of it understanding the box model, how CSS inheritance works, what flexbox and grid are doing, and how specificity resolves conflicts. That was enough.

💡

Four hours of structured fundamentals is not enough to build something complex. But it is enough to stop AI output being a black box. You can read it, catch obvious problems, and ask better follow-up questions. That changes everything about the workflow.

Choosing the constraints

Before starting, I made a few deliberate decisions about scope. Vanilla HTML and CSS only — no JavaScript at this stage, which kept the mental model simple and forced clean, semantic HTML. No CSS frameworks like Tailwind or Bootstrap, because I wanted to understand the design system I was building rather than configuring someone else's. And version control from day one: every meaningful iteration saved as a new file, so I could always roll back.

The Design System

The first real technical challenge was colour. I had a rough palette in mind — navy, amber, blue, slate — but implementing it consistently across a whole site is harder than it sounds. Hardcoded hex values scattered through a stylesheet become a maintenance problem immediately.

Working iteratively with Claude, I built a CSS custom properties system using named base colours and a five-step scale generated by color-mix(). The scale convention — lower numbers lighter, higher numbers darker — mirrors Tailwind's approach, which I found intuitive once I understood the direction.

CSS 
/* Base colour + 5-step scale using color-mix() */
--navy:       #213345;
--navy-50:    color-mix(in srgb, var(--navy) 20%, white);
--navy-300:   color-mix(in srgb, var(--navy) 60%, white);
--navy-500:   var(--navy);
--navy-700:   color-mix(in srgb, var(--navy) 65%, black);
--navy-950:   color-mix(in srgb, var(--navy) 30%, black);

/* Semantic aliases — these are what the rest of the stylesheet uses */
--bg-page:        var(--white);
--bg-subtle:      var(--neutral-50);
--text-primary:   var(--neutral-950);
--text-muted:     var(--neutral-500);

This pattern — base variables feeding semantic aliases — means the whole site can be recoloured by changing a handful of base values. It also means I can read the stylesheet and understand immediately what var(--text-muted) means without looking it up.

Understanding why this architecture works came from the course. Without that foundation, I would have accepted whatever Claude generated without understanding the trade-offs.

The Iterative Build Process

The site was not designed and then built. It was built and then redesigned, repeatedly. Each major iteration involved a prompt to Claude describing what I wanted, a generated output, my own review and editing pass, and then a decision about what to tackle next. The version number in the filename went up with each meaningful change.

  • v1
    First structure — nav, hero, basic sections

    A working skeleton: fixed nav, hero with heading and CTA buttons, placeholder sections. Heavily orange-accented, which was later walked back significantly.

  • v2
    Colour system and design tokens

    Replaced hardcoded hex values with a full CSS variable architecture. This was the most technically dense session — the colour scale, semantic aliases, shadow system, and border tokens all came together here.

  • v3–v4
    Skills section, project cards, experience timeline

    Content sections built out. Skill cards with coloured top borders. Project cards with colour accent stripes and tech badge pills. The timeline using a CSS pseudo-element vertical line.

  • v5–v6
    Colour direction settled — blue primary, orange reserved

    Orange was initially used widely as the primary accent. After reviewing the overall feel, it was reserved only for KPI numbers and the hero eyebrow text. Blue became the primary interactive colour.

  • v7+
    Sub-pages: projects listing and individual project template

    Separate HTML pages with their own page headers, breadcrumb navigation, and layouts — all sharing the same stylesheet. The project page template introduced the two-column article/sidebar layout seen on this page.

How AI Assistance Actually Worked

It is worth being specific about what AI did and did not do in this build, because "I used AI" means very different things depending on how it is used.

What Claude generated

Claude wrote the first draft of most components. Given a description of what I wanted — a sticky nav with a logo on the left and links on the right, a CTA button that pulses subtly on hover — it would produce working HTML and CSS. That first draft was usually close but rarely finished. It needed reviewing, trimming, and adjusting.

What I changed manually

Almost every section had manual edits after generation. Content was entirely mine — Claude does not know my career history, my writing voice, or what I actually want to say about my work. Spacing, sizing, and proportion decisions were often adjusted by eye. Some components were regenerated two or three times with refined prompts before they looked right. And the colour direction decisions — orange in, orange out, blue primary — were aesthetic calls I made after looking at the full page.

ℹ️

The most useful thing about AI in this workflow was not that it wrote perfect code. It was that it eliminated the blank page problem. Starting from a working draft that is 70% right is far faster than starting from nothing, even when the 30% requires real work.

Where it fell short

AI assistance is less useful when the problem is aesthetic rather than technical. "Make this feel more refined" produces output that is different but not necessarily better. The most productive prompts were specific and technical: "Change the skill tag background to use color-mix(in srgb, var(--slate) 5%, white) and add a 1px dashed amber border." Vague prompts produced vague improvements.

It also cannot catch design inconsistencies it cannot see. Several issues — a section that felt cramped, a font size that looked off against the heading — were only visible in the browser and required me to identify the problem and describe it precisely before Claude could help fix it.

Key Design Decisions

No JavaScript

JavaScript was explicitly excluded from this version of the site. This was partly about keeping the complexity manageable while learning, and partly a deliberate choice. Pure HTML and CSS forces you to solve problems at the markup and styling layer, which produces leaner, more maintainable output. The filter functionality on the projects page, for example, uses CSS-only category labels rather than a JS-powered filter — simpler, and one less thing to break.

Uniform skill tag styling

An earlier version had colour-coded skill tags — blue for SQL tools, amber for Python, orange for visualisation. It looked busy and the colour associations felt arbitrary. The settled approach uses a single uniform slate style for all tags, which is cleaner and lets the content speak rather than the decoration.

Version control discipline

Every meaningful iteration was saved as a new numbered file before changes were made. This felt overly cautious at first. It became essential when a colour direction was tried, rejected, and needed to be partially recovered three versions later. Rolling back to a previous iteration is straightforward when each version exists as a discrete file.

The result is a site I understand completely. Every line of CSS has a reason I can explain. If something breaks, I can read the stylesheet and find it. If the design needs to change, I know where to make the change. That level of ownership would not have been possible with a template.

The AI-assisted workflow also produced something I did not expect: a faster feedback loop than working alone would have given me. Each iteration took hours rather than days. The design evolved through many small experiments that would have been impractical to run manually.

Reflections

The four hours of upfront study was the best investment in the project. Without it, the AI workflow degrades into copying and pasting code you cannot evaluate — which is both risky and slow when something goes wrong. With it, the output becomes something you can read, critique, and improve.

If I were starting again, I would spend more time upfront on the design system before building any components. The colour architecture and spacing variables were built partway through the first version, which meant earlier components had to be refactored to use the new variables. Designing the token layer first would have made the whole process cleaner.

The site is still evolving. More project pages, a refined colour system, and eventual JavaScript functionality as my understanding grows. But the foundation is solid, and it is entirely mine.
